## 学习目标与生活例子

一个实验助教接到“查出电机异常原因”的任务，会查手册、看日志、比较证据再给结论。AI 应用也可以围绕模型连接检索、工具和流程；关键是分清每一层负责什么。

## RAG：先找资料，再组织回答

检索增强生成通常把资料切块、建立索引；收到问题时检索相关内容，将其连同问题提供给模型。索引可采用关键词、向量或混合方式。检索不等于训练，也不自动保证回答正确；必须检查检索命中、引用与答案是否相符。

例如查“F107 的 TIM2 在哪条总线上”，先检索参考手册的相关段落，再生成带出处的解释，比只依赖模型记忆更容易核查。

## Agent：围绕目标反复选择下一步

Agent 常指能根据目标、当前状态和工具反馈选择行动的系统。循环可以是“观察 → 计划或决定 → 调用工具 → 读取结果 → 检查是否完成”。固定工作流则按预先设计的分支推进，两者可以结合。没有统一的“用了几个工具就算 Agent”门槛。

## MCP、插件与 Skill 的区别

| 术语 | 解决的问题 | 类比 |
|---|---|---|
| MCP | 让 AI 应用以标准协议连接外部工具、资源与提示等能力 | 约定接口的接线方式 |
| 插件 | 按某个平台约定打包扩展功能，可包括界面、工具、配置等 | 可安装的扩展包 |
| Skill | 为特定任务整理的说明、资源及可选脚本，具体支持依平台 | 一份可复用操作手册 |
| Agent | 根据目标组织模型、状态与行动循环的系统 | 执行任务的助教流程 |

MCP 架构中的 host 承载应用，client 负责连接，server 提供能力。它不是大模型本身，也不是“装上就更聪明”；权限、工具执行和错误处理仍需应用设计。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)

Agent Skills 格式用 `SKILL.md` 等文件描述任务知识并可附带资源。Skill 与模型权重不同，读取操作说明不是训练模型。插件可能打包 Skill，也可能只提供工具，具体看平台定义。[Agent Skills 说明](https://agentskills.io/home)

## 一个容易理解的伪代码

```python
question = read_user_question()          # 收到任务
evidence = search_manual(question)       # 检索资料
draft = model_answer(question, evidence) # 根据上下文生成草稿
checked = verify_citations(draft)        # 校核引用是否支持结论
show_to_user(checked)                    # 返回可核查结果
```

每行都是应用层职责的示意函数，不是可以直接运行的某家 API。第 2 行取得信息不修改权重；第 3 行仍可能产生错误；第 4 行不应只靠“看起来像引用”。真实系统还需要处理找不到资料、工具失败和越权调用。

## AI 与机器人怎样分工

相机图像 → 视觉模型输出位置/类别 → 规划模块给出任务或轨迹 → 传统控制器跟踪速度/位置 → 驱动器执行。语言模型可辅助解释日志、检索手册、生成待审查代码；稳定实时的电机环依旧需要明确采样、延迟与故障处理。

例如“去红色方块旁边”需要视觉定位、坐标转换、路径规划和底层控制共同完成。把大语言模型一句话直接变成无校验电机指令，会遗漏单位、坐标系、时限与执行范围。

## 常见错误与思考题

不要把 RAG 当微调、把 MCP 当云模型、把 Skill 当自动授权，也不要将一次演示成功当成长期可靠性证明。

<details><summary>模型能调用一个文件工具，是否就应该允许它删除任意文件？</summary>不应该。工具能力与任务授权分开设计，应用应限制范围并对重要动作设置合适校验。协议提供连接方式，不替代权限边界。</details>
<details><summary>为什么电机内环不能只依赖网络上的语言模型回答？</summary>内环需要确定的采样节奏和可分析行为；网络延迟、输出格式和推理时间难满足这些要求。高层任务理解与低层实时控制应有清楚接口。</details>
